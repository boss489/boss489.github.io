# StreamBridge와 Saga 패턴 정리

이벤트 기반 아키텍처를 설계할 때는 "메시지를 어디로 보낼 것인가"와 "여러 서비스에 걸친 트랜잭션을 어떻게 다룰 것인가"를 함께 고민하게 된다. Spring Cloud Stream의 `StreamBridge`와 분산 트랜잭션 패턴인 Saga는 각각 이 두 문제를 다루는 대표적인 도구다.

## StreamBridge란 무엇인가

Spring Cloud Stream은 일반적으로 함수형 빈과 바인딩 설정을 기준으로 입력/출력 채널이 고정된다. 즉, 애플리케이션 시작 시점에 "어떤 함수가 어떤 토픽과 연결되는가"가 결정되는 경우가 많다.

하지만 실무에서는 다음과 같은 요구가 자주 나온다.

- 하나의 프로듀서가 상황에 따라 다른 토픽으로 메시지를 보내야 함
- 이벤트 라우팅 대상이 런타임 조건에 따라 달라짐
- 함수형 바인딩 밖에서 메시지를 발행해야 함

이럴 때 `StreamBridge`를 사용하면 동적으로 특정 바인딩 이름으로 메시지를 전송할 수 있다.

## StreamBridge 사용 예시

```java
@Service
public class OrderEventPublisher {

    private final StreamBridge streamBridge;

    public OrderEventPublisher(StreamBridge streamBridge) {
        this.streamBridge = streamBridge;
    }

    public void publish(String bindingName, OrderEvent event) {
        streamBridge.send(bindingName, event);
    }
}
```

예를 들어 주문 상태에 따라 다른 토픽으로 보낼 수 있다.

- 결제 요청: `payment-out-0`
- 배송 요청: `delivery-out-0`
- 실패 보상 이벤트: `compensation-out-0`

이 방식은 정적인 바인딩 모델을 깨지 않으면서도 런타임 유연성을 확보할 수 있다는 장점이 있다.

## StreamBridge가 유용한 상황

1. 라우팅 규칙이 비즈니스 조건에 따라 달라질 때
2. HTTP 요청 처리 후 이벤트를 발행할 때
3. 스케줄러, 배치, 도메인 서비스 계층에서 직접 메시지를 보낼 때

다만 과도하게 사용하면 이벤트 흐름이 설정 파일보다 코드에 분산되어 추적이 어려워질 수 있으므로, 발행 경로를 명확히 관리하는 것이 좋다.

## Saga 패턴이 필요한 이유

모놀리식 시스템에서는 하나의 DB 트랜잭션으로 원자성을 보장할 수 있다. 하지만 MSA에서는 주문, 결제, 재고, 배송 서비스가 각자 다른 데이터 저장소를 가지므로 하나의 글로벌 트랜잭션으로 묶기 어렵다.

Saga 패턴은 이런 상황에서 "최종적 일관성(eventual consistency)"을 달성하기 위한 대표적인 접근이다.

## Saga 패턴의 두 가지 방식

### Choreography 방식
각 서비스가 이벤트를 구독하고, 자신의 작업이 끝나면 다음 이벤트를 발행한다.

- 중앙 조정자가 없음
- 서비스 간 결합도가 비교적 낮음
- 단순 흐름에서는 구현이 간단함

하지만 흐름이 복잡해지면 어떤 이벤트가 전체 프로세스를 어디까지 진행시켰는지 추적하기 어려워질 수 있다.

### Orchestration 방식
중앙 오케스트레이터가 전체 흐름을 제어하고, 각 서비스에 명령 또는 이벤트를 전달한다.

- 프로세스 가시성이 높음
- 복잡한 비즈니스 플로우에 적합
- 실패 시 보상 트랜잭션 관리가 상대적으로 명확함

반면 중앙 제어 컴포넌트가 추가되므로 설계 복잡도는 높아진다.

## 보상 트랜잭션이 핵심이다

Saga는 전통적인 ACID 롤백이 아니다. 이미 완료된 로컬 트랜잭션을 "되돌리는 별도의 비즈니스 동작"이 필요하다.

예를 들어 주문 처리 흐름이 다음과 같다고 가정해보자.

1. 주문 생성
2. 결제 승인
3. 재고 차감
4. 배송 요청

이때 4단계에서 실패하면 다음과 같은 보상 작업이 필요할 수 있다.

- 재고 복구
- 결제 취소
- 주문 상태 취소 처리

즉, Saga의 본질은 "원자성 보장"이 아니라 "실패를 수용하면서 일관성을 회복하는 설계"다.

## 이벤트 기반 아키텍처에서의 장점

이벤트는 서비스 장애 격리와 비동기 복구에 유리하다.

- 특정 모듈이 일시적으로 실패해도 전체 요청을 동기적으로 막지 않을 수 있음
- 서비스 복구 후 미처리 이벤트를 다시 소비할 수 있음
- 재시도, DLQ, 보상 이벤트 설계를 통해 복원력 확보 가능

즉, 이벤트 드리븐 아키텍처에서는 장애를 없애는 것이 아니라 장애 이후에도 흐름을 이어갈 수 있도록 설계하는 것이 중요하다.

## 실무에서 함께 고려할 점

### 1. 멱등성
재처리나 중복 이벤트 수신이 발생할 수 있으므로 각 서비스는 멱등하게 설계되어야 한다.

### 2. 이벤트 순서
순서가 중요한 도메인에서는 파티션 키 설계와 소비 전략을 신중히 정해야 한다.

### 3. 상태 추적
Saga 진행 상태를 추적할 수 있는 로그, 상태 테이블, 모니터링 지표가 필요하다.

### 4. 실패 정책
재시도 횟수, 타임아웃, DLQ 이동 조건, 보상 트리거 시점을 명확히 해야 한다.

## 결론

`StreamBridge`는 런타임 조건에 따라 메시지 발행 대상을 유연하게 바꾸는 도구이고, Saga 패턴은 여러 서비스에 걸친 비즈니스 일관성을 유지하기 위한 분산 트랜잭션 전략이다.

- `StreamBridge`: 동적 이벤트 발행
- `Saga`: 서비스 간 최종적 일관성 확보

이 두 개념을 함께 이해하면 MSA와 이벤트 기반 시스템에서 훨씬 실용적인 설계를 할 수 있다.
