# Chapter 03. 컴퓨팅 비용 최적화
## 실측 부하에 맞는 실행 환경 선택하기

> **학습 목표**
>
> - Right Sizing과 Auto Scaling으로 유휴 컴퓨팅을 줄일 수 있다.
> - Graviton과 Spot 도입 전에 필요한 호환성과 중단 검증을 설명할 수 있다.
> - Fargate, EC2와 Lambda를 워크로드 특성으로 비교할 수 있다.

---

# 비용 폭증 시나리오

야간 트래픽이 거의 없는데도 최대 트래픽 기준의 인스턴스가 계속 실행되는 상황을 가정한다.

평균 CPU만 보고 크기를 줄이면 JVM 메모리, GC와 순간 부하를 놓쳐 장애가 날 수 있다.

컴퓨팅 비용은 인스턴스 크기뿐 아니라 실행 시간, 확장 속도와 운영 방식의 영향을 함께 받는다.

---

# 핵심 정의

## Right Sizing

CPU, 메모리, 네트워크와 지연 지표를 근거로 실행 자원의 종류와 크기를 맞추는 활동이다.

## Auto Scaling

수요 지표와 정책에 따라 용량을 자동으로 늘리거나 줄이는 방식이다.

## Schedule

예측 가능한 비운영 시간에 개발 환경이나 배치 자원을 중지하는 정책이다.

## Spot

가용 용량을 할인된 모델로 사용하되 중단 가능성을 애플리케이션이 감수하는 방식이다.

## Graviton

Arm 기반 AWS 프로세서 계열로 런타임과 네이티브 의존성 호환성 검증이 필요하다.

---

# 비용 흐름

```
요청량·지연·CPU·메모리
  -> Right Sizing
  -> Auto Scaling 정책
  -> EC2 / Fargate / Lambda 선택
  -> On-Demand + Spot 조합
  -> 처리량과 SLO 검증
  -> 단위 컴퓨팅 비용
```

이 흐름에서 사용량이 생성되는 지점과 청구 데이터에서 보이는 지점을 연결해야 한다.

---

# 비교표

| 방식 | 강점 | 주의점 |
|---|---|---|
| EC2 | 제어와 지속 부하 효율 | 서버와 용량 운영 |
| Fargate | 서버 관리 감소 | Task 크기와 지속 사용량 |
| Lambda | 이벤트·변동 부하 | 실행 제한과 콜드 스타트 |
| Spot | 중단 허용 작업 효율 | 중단 대응 필수 |

비교표는 절대적인 우열이 아니라 워크로드에 맞는 선택 기준을 제공한다.

---

# Cost Explorer와 AWS CLI

다음 명령은 예시 기간의 데이터를 조회하며 실행 계정의 권한과 실제 날짜를 확인해야 한다.

```bash
aws cloudwatch get-metric-data \
  --metric-data-queries file://compute-metrics.json \
  --start-time 2026-08-01T00:00:00Z \
  --end-time 2026-08-08T00:00:00Z
aws ec2 describe-instance-types --instance-types m7g.large m7i.large
```

CLI 결과는 청구 확정 시점과 데이터 지연을 고려해 해석한다.

특정 가격 수치는 문서에 고정하지 않고 Region, 시점과 구매 모델에 맞는 공식 가격 정보를 확인한다.

---

# Spring Boot 운영자가 통제할 수 있는 요소

Actuator와 Micrometer로 요청률, p95 지연, JVM 힙, GC와 스레드 사용량을 수집한다.

컨테이너 메모리 제한과 JVM `MaxRAMPercentage`를 함께 조정해 OOM과 과도한 여유를 피한다.

Spot 중단 시 SIGTERM을 받아 새 요청을 중단하고 처리 중 작업을 안전하게 마무리한다.

---

# 실무 적용

## 1단계: 기준선 만들기

변경 전 최소 한 주기의 비용, 사용량, 처리량과 SLO를 같은 시간 범위로 저장한다.

## 2단계: 원인 분리하기

최소 일주일 이상의 피크와 저부하 구간을 보고 CPU뿐 아니라 메모리와 네트워크를 함께 판단한다.

## 3단계: 작은 변경 적용하기

개발 환경은 업무 시간 스케줄을 적용하되 필요한 사람이 안전하게 재시작할 경로를 제공한다.

## 4단계: 가격 조건 확인하기

Graviton 전환 전 JDK, 컨테이너 이미지, JNI 라이브러리와 모니터링 에이전트를 부하 시험한다.

## 5단계: 효과 검증하기

변경 후 총비용뿐 아니라 단위 비용, 지연, 오류율과 운영 부담이 어떻게 달라졌는지 확인한다.

---

# 운영 함정

평균 CPU 하나로 Right Sizing하면 짧은 피크와 메모리 병목을 숨길 수 있다.

Auto Scaling의 최소 용량을 지나치게 낮추면 확장 전까지 지연과 오류가 증가할 수 있다.

Spot을 상태 저장 노드나 중단 불가능한 단일 작업에 그대로 적용하면 데이터와 가용성을 잃을 수 있다.

---

# 비용과 성능의 Trade-off

여유 용량은 급증 대응을 빠르게 하지만 평시 유휴 비용을 만든다.

Fargate와 Lambda는 운영 부담을 줄일 수 있지만 모든 지속 부하에서 자동으로 더 저렴한 것은 아니다.

최적 선택은 처리 패턴, 시작 시간, 상태성, 팀의 운영 역량과 SLO를 함께 비교해 정한다.

비용 최적화는 단순한 최저가 선택이 아니라 비즈니스 가치, 가용성, 성능과 운영 가능성 사이의 균형을 찾는 일이다.

---

# 점검 체크리스트

- 비용 변화의 시작 시각과 배포 시각을 비교했는가.

- 서비스, 계정, 태그와 사용 유형으로 비용을 분해했는가.

- 변경 전후의 단위 비용과 SLO를 함께 비교했는가.

- 되돌리기 절차와 담당 owner가 정해져 있는가.

- 최신 Region과 구매 모델의 가격 조건을 확인했는가.

---

# 핵심 요약

Right Sizing은 CPU뿐 아니라 JVM 메모리, 지연과 피크를 근거로 수행한다.

예측 가능한 수요에는 스케줄과 Auto Scaling을 조합한다.

Graviton과 Spot은 호환성과 중단 복구를 검증한 뒤 단계적으로 적용한다.
