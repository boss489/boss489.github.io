# Chapter 08. FinOps 실천
## 비용을 팀의 반복 가능한 운영 과정으로 만들기

> **학습 목표**
>
> - detect, allocate, optimize, govern 순환을 운영 절차로 만들 수 있다.
> - 주문당 비용 같은 Unit Economics를 계산하고 해석할 수 있다.
> - 주기적인 비용 review와 명확한 owner 체계를 설계할 수 있다.

---

# 비용 폭증 시나리오

비용 절감 태스크포스가 한 번 정리한 뒤 몇 달 만에 비용이 다시 증가한 상황을 가정한다.

소유자와 검토 주기가 없으면 미태그 자원, 과도한 로그와 유휴 개발 환경이 반복해서 생긴다.

월 전체 청구액만 보면 주문 증가로 생긴 건강한 비용과 비효율로 생긴 비용을 구분하기 어렵다.

---

# 핵심 정의

## Detect

비용 추세, Budget과 이상 탐지로 변화 신호를 발견하는 단계다.

## Allocate

계정, 태그와 Cost Categories를 사용해 비용을 제품과 팀에 배분하는 단계다.

## Optimize

사용량, 아키텍처와 구매 모델을 바꾸고 효과를 검증하는 단계다.

## Govern

정책, owner, review와 자동화로 개선 상태를 유지하는 단계다.

## Unit Economics

비용을 주문, 사용자 또는 API 성공 건수 같은 비즈니스 단위로 나눈 관점이다.

---

# 비용 흐름

```
detect
  -> allocate
       -> optimize
            -> govern
                 -> detect
비용 + 주문 수 + SLO
  -> cost/order와 owner action
```

이 흐름에서 사용량이 생성되는 지점과 청구 데이터에서 보이는 지점을 연결해야 한다.

---

# 비교표

| 지표 | 의미 | 주의점 |
|---|---|---|
| 총비용 | 전체 지출 규모 | 성장 효과 혼재 |
| cost/order | 주문 단위 효율 | 주문 정의 일관성 |
| coverage | 할인 적용 범위 | 효율과 별개 |
| utilization | 약정 사용 정도 | 수요 변화 반영 |

비교표는 절대적인 우열이 아니라 워크로드에 맞는 선택 기준을 제공한다.

---

# Cost Explorer와 AWS CLI

다음 명령은 예시 기간의 데이터를 조회하며 실행 계정의 권한과 실제 날짜를 확인해야 한다.

```bash
aws ce get-cost-and-usage \
  --time-period Start=2026-08-01,End=2026-08-08 \
  --granularity DAILY \
  --metrics AmortizedCost \
  --group-by Type=TAG,Key=Product
aws ce get-anomalies --date-interval StartDate=2026-08-01,EndDate=2026-08-08
```

CLI 결과는 청구 확정 시점과 데이터 지연을 고려해 해석한다.

특정 가격 수치는 문서에 고정하지 않고 Region, 시점과 구매 모델에 맞는 공식 가격 정보를 확인한다.

---

# Spring Boot 운영자가 통제할 수 있는 요소

서비스는 성공 주문 수, 유효 API 호출 수와 처리 데이터량을 일관된 Micrometer 지표로 제공한다.

로그와 추적 샘플링 변경은 장애 분석 가능성을 훼손하지 않도록 환경별 정책으로 관리한다.

각 서비스 저장소에 비용 owner와 주요 단위 지표를 운영 문서로 기록한다.

---

# 실무 적용

## 1단계: 기준선 만들기

변경 전 최소 한 주기의 비용, 사용량, 처리량과 SLO를 같은 시간 범위로 저장한다.

## 2단계: 원인 분리하기

주간 review에서는 이상과 즉시 조치를 확인하고 월간 review에서는 추세와 약정과 구조 개선을 다룬다.

## 3단계: 작은 변경 적용하기

개선 항목마다 owner, 기한, 예상 효과, SLO 위험과 검증 지표를 지정한다.

## 4단계: 가격 조건 확인하기

절감액만 발표하지 않고 변경 후 cost/order, 오류율, 지연과 운영 시간을 함께 비교한다.

## 5단계: 효과 검증하기

변경 후 총비용뿐 아니라 단위 비용, 지연, 오류율과 운영 부담이 어떻게 달라졌는지 확인한다.

---

# 운영 함정

FinOps를 재무팀만의 비용 삭감 업무로 두면 개발자가 사용량 원인을 개선하기 어렵다.

단위 비용 분모가 팀마다 다르면 제품 간 비교가 왜곡된다.

자동 삭제 정책에 예외와 복구 절차가 없으면 필요한 자원과 증거 데이터를 잃을 수 있다.

---

# 비용과 성능의 Trade-off

정교한 배부 모델은 책임성을 높이지만 유지 비용과 논쟁도 늘릴 수 있다.

강한 거버넌스는 낭비를 막지만 실험 속도를 늦출 수 있으므로 샌드박스와 한도를 함께 제공한다.

FinOps의 성공은 일회성 최저 비용이 아니라 가치와 안정성을 지키는 반복 가능한 의사결정에 있다.

비용 최적화는 단순한 최저가 선택이 아니라 비즈니스 가치, 가용성, 성능과 운영 가능성 사이의 균형을 찾는 일이다.

---

# 점검 체크리스트

- 비용 변화의 시작 시각과 배포 시각을 비교했는가.

- 서비스, 계정, 태그와 사용 유형으로 비용을 분해했는가.

- 변경 전후의 단위 비용과 SLO를 함께 비교했는가.

- 되돌리기 절차와 담당 owner가 정해져 있는가.

- 최신 Region과 구매 모델의 가격 조건을 확인했는가.

---

# 핵심 요약

FinOps는 detect, allocate, optimize, govern을 반복하는 운영 방식이다.

총비용과 함께 cost/order 같은 단위 경제성을 본다.

모든 개선에 owner, review 주기와 SLO 검증을 연결한다.
