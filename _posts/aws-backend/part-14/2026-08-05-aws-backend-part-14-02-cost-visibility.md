# Chapter 02. 비용 가시성
## 비용을 발견하고 소유자에게 연결하기

> **학습 목표**
>
> - Cost Explorer, Budgets와 Cost Anomaly Detection의 역할을 구분할 수 있다.
> - CUR과 Data Exports를 상세 분석에 활용하는 흐름을 설명할 수 있다.
> - 태그, Cost Categories와 계정 분리로 비용을 할당할 수 있다.

---

# 비용 폭증 시나리오

신규 배포 뒤 청구 예상치가 늘었지만 어느 팀과 기능이 원인인지 알 수 없는 상황을 가정한다.

공통 계정에 태그 없이 자원을 만들면 서비스 화면은 보여도 비용 소유자와 비즈니스 목적을 연결하기 어렵다.

가시성이 없으면 대응은 늦고 각 팀은 자신의 변경이 전체 비용에 미친 영향을 학습하지 못한다.

---

# 핵심 정의

## Cost Explorer

기간, 서비스, 계정, 태그 같은 차원으로 비용과 사용량을 탐색하는 도구다.

## Budgets

정한 비용 또는 사용량 임계치에 대한 계획 대비 알림과 선택적 조치를 제공한다.

## Cost Anomaly Detection

과거 패턴을 기준으로 비정상적인 비용 변화를 탐지하고 구독자에게 알린다.

## CUR와 Data Exports

세부 청구 데이터를 S3 등으로 내보내 분석하는 방식이며 Data Exports는 내보낼 데이터와 SQL 기반 선택 관점을 제공한다.

## Cost Categories

계정, 태그와 서비스 규칙을 비즈니스 분류로 묶는 기능이다.

---

# 비용 흐름

```
AWS 사용량
  -> Billing 데이터
  -> Cost Explorer ── 추세 탐색
  -> Budgets ─────── 계획 임계치
  -> Anomaly Detection ─ 이상 탐지
  -> CUR / Data Exports ─ 상세 분석
  -> Tag / Category / Account ─ 소유자 할당
```

이 흐름에서 사용량이 생성되는 지점과 청구 데이터에서 보이는 지점을 연결해야 한다.

---

# 비교표

| 도구 | 주요 질문 | 특징 |
|---|---|---|
| Cost Explorer | 어디서 얼마나 변했는가 | 대화형 분석 |
| Budgets | 계획을 넘을 가능성이 있는가 | 임계치 알림 |
| Anomaly Detection | 평소와 다른가 | 패턴 기반 탐지 |
| CUR·Data Exports | 어떤 사용 항목인가 | 상세 데이터 분석 |

비교표는 절대적인 우열이 아니라 워크로드에 맞는 선택 기준을 제공한다.

---

# Cost Explorer와 AWS CLI

다음 명령은 예시 기간의 데이터를 조회하며 실행 계정의 권한과 실제 날짜를 확인해야 한다.

```bash
aws ce get-cost-and-usage \
  --time-period Start=2026-08-01,End=2026-08-08 \
  --granularity DAILY \
  --metrics UnblendedCost \
  --group-by Type=TAG,Key=CostCenter
aws budgets describe-budgets --account-id 123456789012
```

CLI 결과는 청구 확정 시점과 데이터 지연을 고려해 해석한다.

특정 가격 수치는 문서에 고정하지 않고 Region, 시점과 구매 모델에 맞는 공식 가격 정보를 확인한다.

---

# Spring Boot 운영자가 통제할 수 있는 요소

애플리케이션 이름, 환경, 팀, 비용 센터를 배포 메타데이터와 자원 태그에 일관되게 전달한다.

배포 이벤트를 기록해 비용 이상 발생 시 코드 변경과 인프라 변경을 빠르게 대조한다.

주문 수와 API 호출 수 같은 비즈니스 지표를 비용 기간과 동일한 단위로 집계한다.

---

# 실무 적용

## 1단계: 기준선 만들기

변경 전 최소 한 주기의 비용, 사용량, 처리량과 SLO를 같은 시간 범위로 저장한다.

## 2단계: 원인 분리하기

운영, 개발과 실험 워크로드는 계정을 분리해 권한 경계와 비용 경계를 함께 만든다.

## 3단계: 작은 변경 적용하기

필수 태그 정책을 정하고 미태그 비용을 정기적으로 별도 보고한다.

## 4단계: 가격 조건 확인하기

Budget 알림 수신자와 이상 탐지 대응 소유자를 지정하고 알림만 쌓이지 않게 한다.

## 5단계: 효과 검증하기

변경 후 총비용뿐 아니라 단위 비용, 지연, 오류율과 운영 부담이 어떻게 달라졌는지 확인한다.

---

# 운영 함정

Budget은 비용을 자동으로 이해하거나 모든 지출을 즉시 차단하는 장치가 아니다.

비용 데이터에는 지연과 조정이 있을 수 있으므로 실시간 장애 지표처럼 취급하면 안 된다.

태그는 일부 비용 항목에 소급 적용되지 않을 수 있으므로 생성 시점부터 강제하는 편이 안전하다.

---

# 비용과 성능의 Trade-off

세밀한 태그와 상세 내보내기는 분석력을 높이지만 데이터 관리와 쿼리 비용도 만든다.

계정 분리는 명확성을 높이지만 공통 자원 배분 규칙과 운영 체계가 필요하다.

가시성의 목적은 보고서 생산이 아니라 담당자가 빠르게 행동할 수 있는 정보 제공이다.

비용 최적화는 단순한 최저가 선택이 아니라 비즈니스 가치, 가용성, 성능과 운영 가능성 사이의 균형을 찾는 일이다.

---

# 점검 체크리스트

- 비용 변화의 시작 시각과 배포 시각을 비교했는가.

- 서비스, 계정, 태그와 사용 유형으로 비용을 분해했는가.

- 변경 전후의 단위 비용과 SLO를 함께 비교했는가.

- 되돌리기 절차와 담당 owner가 정해져 있는가.

- 최신 Region과 구매 모델의 가격 조건을 확인했는가.

---

# 핵심 요약

탐색, 계획 알림, 이상 탐지와 상세 분석 도구의 역할을 구분한다.

비용을 태그, Cost Categories와 계정으로 소유자에게 할당한다.

가시성에는 알림을 처리할 owner와 정기적인 검토 절차가 함께 있어야 한다.
