# Chapter 07. Savings Plans와 Reserved Instances
## 기준선을 측정한 뒤 할인 약정하기

> **학습 목표**
>
> - Savings Plans와 Reserved Instances의 할인 범위와 유연성을 비교할 수 있다.
> - 할인 적용과 용량 예약이 서로 다른 개념임을 설명할 수 있다.
> - 온디맨드 기준선을 근거로 과약정 위험을 관리할 수 있다.

---

# 비용 폭증 시나리오

일시적인 캠페인 피크를 평상시 사용량으로 오해하고 장기 약정을 크게 구매한 상황을 가정한다.

몇 달 뒤 아키텍처를 Lambda나 Fargate로 변경하면 약정 범위에 따라 할인 활용률이 낮아질 수 있다.

할인을 받았더라도 사용하지 못한 약정이 많으면 전체 비용 최적화에는 실패한 것이다.

---

# 핵심 정의

## Savings Plans

일정 기간 동안 시간당 컴퓨팅 사용 금액을 약정하고 범위에 따라 할인 적용 유연성을 얻는 모델이다.

## Compute Savings Plans

지원되는 컴퓨팅 사용 전반에 비교적 넓은 유연성을 제공하는 약정 유형이다.

## EC2 Instance Savings Plans

선택한 리전과 인스턴스 패밀리 범위에 더 제한된 대신 조건이 다른 유형이다.

## Reserved Instances

EC2 또는 서비스별 조건에 따라 할인을 제공하며 표준·전환 가능 여부와 범위를 확인해야 한다.

## 용량 예약

특정 AZ에서 EC2 용량 사용 가능성을 확보하는 개념으로 할인 약정과 자동으로 동일하지 않다.

---

# 비용 흐름

```
온디맨드 사용량 이력
  -> 안정적 기준선 계산
  -> 아키텍처 변경 계획 확인
  -> Savings Plans / RI 비교
  -> 약정 범위와 기간 선택
  -> utilization·coverage 추적
  -> 부족분은 온디맨드로 유지
```

이 흐름에서 사용량이 생성되는 지점과 청구 데이터에서 보이는 지점을 연결해야 한다.

---

# 비교표

| 항목 | Savings Plans | Reserved Instances |
|---|---|---|
| 약정 기준 | 시간당 사용 금액 | 특정 서비스 구성 조건 |
| 유연성 | 유형별 범위가 다름 | 표준·전환 조건이 다름 |
| 용량 확보 | 별도 검토 | 할인과 예약 속성을 구분 |
| 핵심 위험 | 미사용 약정 | 변경으로 할인 미적용 |

비교표는 절대적인 우열이 아니라 워크로드에 맞는 선택 기준을 제공한다.

# Cost Explorer와 AWS CLI

다음 명령은 예시 기간의 데이터를 조회하며 실행 계정의 권한과 실제 날짜를 확인해야 한다.

```bash
aws ce get-savings-plans-utilization \
  --time-period Start=2026-08-01,End=2026-08-08
aws ce get-savings-plans-coverage \
  --time-period Start=2026-08-01,End=2026-08-08
aws ce get-reservation-utilization \
  --time-period Start=2026-08-01,End=2026-08-08
```

CLI 결과는 청구 확정 시점과 데이터 지연을 고려해 해석한다.

특정 가격 수치는 문서에 고정하지 않고 Region, 시점과 구매 모델에 맞는 공식 가격 정보를 확인한다.

# Spring Boot 운영자가 통제할 수 있는 요소

애플리케이션 팀은 예정된 컨테이너 전환, Graviton 전환과 서비스 종료 일정을 FinOps 담당자에게 공유한다.

배포별 최소 용량과 실제 트래픽 기준선을 기록해 약정 가능한 지속 사용량을 구분한다.

성능 개선으로 줄어들 컴퓨팅 사용량을 반영한 뒤 약정을 결정한다.

---

# 실무 적용

## 1단계: 기준선 만들기

변경 전 최소 한 주기의 비용, 사용량, 처리량과 SLO를 같은 시간 범위로 저장한다.

## 2단계: 원인 분리하기

먼저 Right Sizing과 스케줄링을 적용한 온디맨드 기준선을 충분한 기간 측정한다.

## 3단계: 작은 변경 적용하기

확실한 최소 사용량 일부부터 약정하고 나머지는 온디맨드로 남겨 변화를 흡수한다.

## 4단계: 가격 조건 확인하기

매월 utilization과 coverage를 함께 보고 미사용 약정과 미할인 사용량을 구분한다.

## 5단계: 효과 검증하기

변경 후 총비용뿐 아니라 단위 비용, 지연, 오류율과 운영 부담이 어떻게 달라졌는지 확인한다.

---

# 운영 함정

높은 할인율만 보고 약정하면 서비스 축소나 이전 때 과약정이 남을 수 있다.

할인 약정을 구매했다고 특정 AZ의 인스턴스 시작 용량이 항상 보장되는 것은 아니다.

coverage만 높이고 utilization이 낮으면 약정을 과도하게 보유했을 가능성이 있다.

---

# 비용과 성능의 Trade-off

더 긴 기간과 더 강한 결제 조건은 할인 가능성을 높일 수 있지만 사업 변화에 대한 유연성을 줄인다.

넓은 적용 범위는 변경에 유리하고 제한된 범위는 조건에 따라 다른 할인 특성을 가질 수 있다.

가격과 상품 조건은 Region, 시점과 모델에 따라 바뀌므로 구매 직전 공식 문서와 추천을 다시 확인한다.

비용 최적화는 단순한 최저가 선택이 아니라 비즈니스 가치, 가용성, 성능과 운영 가능성 사이의 균형을 찾는 일이다.

---

# 점검 체크리스트

- 비용 변화의 시작 시각과 배포 시각을 비교했는가.

- 서비스, 계정, 태그와 사용 유형으로 비용을 분해했는가.

- 변경 전후의 단위 비용과 SLO를 함께 비교했는가.

- 되돌리기 절차와 담당 owner가 정해져 있는가.

- 최신 Region과 구매 모델의 가격 조건을 확인했는가.

---

# 핵심 요약

약정은 최적화 이후 남은 안정적인 온디맨드 기준선에 적용한다.

Savings Plans와 RI는 범위와 유연성을 비교하고 용량 예약과 구분한다.

utilization과 coverage를 지속 검토해 과약정을 관리한다.
