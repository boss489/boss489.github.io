# Chapter 01. Monitoring Overview
## 관측 데이터로 운영 상태를 설명하는 방법

> **학습 목표**
>
> - 모니터링과 옵저버빌리티의 차이를 설명할 수 있다.
> - 로그·메트릭·트레이스의 역할을 구분할 수 있다.

> - 증상에서 원인으로 이동하는 조사 순서를 설계할 수 있다.

# 왜 필요한가

금요일 할인 행사에서 주문 API 응답 시간이 평소보다 느려졌다고 가정한다.
고객 문의만으로는 전체 장애인지 특정 결제 수단의 문제인지 판단할 수 없다.
요청률과 오류율은 메트릭으로 감지하고 실패 문맥은 로그에서 확인해야 한다.
여러 서비스를 지난 요청의 병목은 트레이스로 찾아야 한다.
세 신호가 같은 서비스와 요청 식별자로 연결되어야 복구 시간이 줄어든다.

관측 데이터는 많이 모으는 것이 목적이 아니라 고객 영향과 다음 행동을 빠르게 결정하기 위한 근거이다.

---

# Monitoring Overview이란?

모니터링은 미리 정한 상태와 임계값을 지속해서 확인하는 활동이며 옵저버빌리티는 외부 신호로 내부 상태를 추론할 수 있는 시스템의 성질이다.

신호의 이름과 책임 경계를 먼저 정해야 여러 팀이 같은 데이터를 같은 의미로 해석할 수 있다.

---

# 동작 흐름

```
고객 요청
  │
  ▼
ALB ──▶ Spring Boot 주문 API ──▶ 결제 API
  │              │                    │
  ├─ Metrics     ├─ JSON Logs         └─ Trace
  │              │
  └──────── CloudWatch / ADOT ────────┘
                    │
          Alarm ─ Dashboard ─ Runbook
```

흐름은 다음 순서로 이해한다.

1. 금요일 할인 행사에서 주문 API 응답 시간이 평소보다 느려졌다고 가정한다.
2. 고객 문의만으로는 전체 장애인지 특정 결제 수단의 문제인지 판단할 수 없다.
3. 요청률과 오류율은 메트릭으로 감지하고 실패 문맥은 로그에서 확인해야 한다.
4. 여러 서비스를 지난 요청의 병목은 트레이스로 찾아야 한다.

각 단계는 실패할 수 있으므로 수집 누락과 전달 지연도 별도 상태로 다룬다.

# 핵심 개념

| 개념 | 의미 | 쇼핑몰 예시 |
|---|---|---|
| 로그 | 개별 사건의 문맥 | 예외 원인과 주문 상태 조사 |
| 메트릭 | 시간에 따른 숫자 | 오류율과 지연 감지 |
| 트레이스 | 분산 요청 경로 | 서비스 간 병목 분석 |
| 이벤트 | 상태 변경 기록 | 배포와 설정 변경 확인 |
| SLI | 측정 가능한 서비스 지표 | 성공률과 지연 시간 |
| SLO | SLI의 목표 범위 | 월간 성공률 목표 |

개념을 독립적으로 외우기보다 하나의 장애 질문에 어떤 개념이 답하는지 연결한다.

# AWS CLI 설정과 조회

다음 명령은 이름과 ARN을 실습 환경에 맞게 바꿔 실행한다.

```bash
aws cloudwatch list-metrics --namespace ShoppingMall/Order
aws logs describe-log-groups --log-group-name-prefix /ecs/order-api
aws cloudwatch describe-alarms --alarm-name-prefix order-api
```

CLI 실행 역할에는 조회와 변경에 필요한 최소 권한만 부여한다.

운영 변경은 콘솔에서 임의로 수행하지 않고 IaC와 리뷰 절차로 재현 가능하게 관리한다.

# Spring Boot 3.x와 Java 17 연동

Actuator와 Micrometer로 HTTP 요청 수와 지연 시간을 노출한다.
로그에는 service, environment, requestId, orderId, errorCode를 구조화해 기록한다.
OpenTelemetry SDK 또는 Java Agent로 trace context를 전파한다.
관측 코드가 비즈니스 로직을 침범하지 않도록 공통 필터와 설정으로 분리한다.
민감한 개인정보와 결제 정보는 어떤 신호에도 기록하지 않는다.

생성자 주입을 사용하면 관측 구현을 테스트 대역으로 교체하고 의존성을 명확히 할 수 있다.

```java
@Service
public class CheckoutObservationService {
    private final MeterRegistry meterRegistry;

    public CheckoutObservationService(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    public void recordSuccess(String paymentProvider) {
        meterRegistry.counter("checkout.success",
                "provider", paymentProvider).increment();
    }
}
```

provider 값은 허용 목록으로 제한하고 주문 번호나 사용자 ID는 tag로 사용하지 않는다.

# 실무 운영

- 서비스 수준 대시보드는 요청률, 오류율, 지연 시간을 첫 화면에 배치한다.
- 인프라 수준에서는 CPU, 메모리, 연결 수, 큐 적체를 함께 본다.
- 알람에는 소유 팀, 영향, 확인 링크, 즉시 실행할 runbook을 포함한다.
- 배포 시각과 기능 플래그 변경을 주석이나 이벤트로 남긴다.
- 정상 상태의 기준선을 먼저 수집한 뒤 임계값을 정한다.

## 운영 점검 순서

1. 고객 영향과 시작 시각을 확인한다.
2. 최근 배포와 구성 변경을 확인한다.
3. 서비스 수준 신호에서 영향 범위를 좁힌다.
4. 로그와 트레이스로 실패 문맥을 찾는다.
5. 완화 조치를 수행하고 지표 회복을 검증한다.
6. 타임라인과 재발 방지 작업을 기록한다.

# 비용과 성능 고려사항

- 수집량, 저장 기간, 조회량, 대시보드와 알람 수, 트레이스 샘플 수가 비용에 영향을 준다.
- 모든 데이터를 무기한 보관하지 않고 운영·감사 목적에 맞춰 보존 기간을 정한다.
- 고카디널리티 식별자를 메트릭 차원으로 사용하지 않는다.
- 장애 조사에 필요한 품질을 유지하면서 샘플링과 집계를 적용한다.

정확한 단가는 Region과 시점에 따라 달라지므로 공식 요금 페이지와 실제 사용량으로 확인한다.

비용 최적화는 데이터를 무조건 버리는 일이 아니라 질문에 답하지 못하는 데이터를 줄이는 일이다.

# 기억할 내용

- 모니터링과 옵저버빌리티의 차이를 설명할 수 있다.
- 로그·메트릭·트레이스의 역할을 구분할 수 있다.
- 쇼핑몰의 SLI와 SLO를 정의할 수 있다.
- 증상에서 원인으로 이동하는 조사 순서를 설계할 수 있다.
- 로그·메트릭·트레이스는 공통 서비스와 환경 정보로 연결한다.
- 개인정보와 인증 정보는 관측 데이터에 남기지 않는다.
- 수집량과 카디널리티와 보존 기간을 운영 정책으로 관리한다.
- 알람은 소유자와 runbook이 있을 때 행동 가능한 신호가 된다.
