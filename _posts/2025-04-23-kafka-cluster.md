# 카프카 클러스터 기본 구조

Kafka를 단일 서버처럼 사용하다가 운영 환경으로 넘어가면 가장 먼저 이해해야 하는 개념이 클러스터 구조다. 브로커, 컨트롤러, 리더 파티션, 복제본이 어떻게 협력하는지 이해해야 고가용성과 장애 대응 방식을 제대로 해석할 수 있다.

## 카프카 클러스터란 무엇인가

Kafka 클러스터는 여러 대의 서버가 함께 하나의 메시징 시스템을 구성하는 구조다. 각 서버는 일반적으로 Kafka Broker 프로세스를 실행하며, 클러스터 전체가 토픽 데이터와 메타데이터를 분산 관리한다.

- 서버 수는 1대일 수도 있고 N대일 수도 있음
- 운영 환경에서는 보통 다중 브로커 구성을 사용
- 목적은 확장성, 내구성, 고가용성 확보

## Broker의 역할

Broker는 Kafka에서 실제 데이터를 읽고 쓰는 핵심 서버다.

- Producer의 쓰기 요청 처리
- Consumer의 읽기 요청 처리
- 토픽 파티션 저장
- 복제본 동기화 수행

즉, Broker는 데이터의 저장소이자 네트워크 요청을 처리하는 실질적인 작업 노드다.

## Controller의 역할

Controller는 클러스터 메타데이터를 관리하는 리더 역할을 한다.

- 브로커 상태 변화 감지
- 파티션 리더 선출
- 복제 상태 관리
- 장애 발생 시 메타데이터 갱신

Broker가 데이터 평면(data plane)을 담당한다면, Controller는 제어 평면(control plane)을 담당한다고 볼 수 있다.

## 단일 서버와 다중 서버의 차이

개발 환경에서는 한 서버가 Broker와 Controller 역할을 동시에 수행하는 경우가 많다.

- `broker + controller`: 단일 서버 구성

하지만 운영 환경에서는 여러 Broker가 존재하고, 그중 하나 또는 일부가 Controller 역할을 맡는다. 이 구조 덕분에 특정 서버 장애가 전체 서비스 중단으로 바로 이어지지 않는다.

## 파티션 리더와 복제본

Kafka의 각 토픽은 여러 파티션으로 나뉠 수 있고, 각 파티션에는 리더와 복제본이 존재한다.

- 리더 파티션: 읽기/쓰기 요청의 기준점
- 팔로워 복제본: 리더 데이터를 복제하여 내구성 확보

중요한 점은 "모든 토픽의 리더가 한 브로커에 몰리지 않는다"는 것이다. 각 토픽, 각 파티션의 리더는 서로 다른 브로커에 분산될 수 있다. 이 분산 덕분에 부하가 나뉘고, 특정 서버 장애 시에도 전체 영향이 제한된다.

## 고가용성이 만들어지는 방식

Kafka가 고가용성을 제공하는 이유는 단순히 서버가 여러 대라서가 아니다. 핵심은 복제와 리더 전환 메커니즘이다.

1. Producer가 리더 파티션에 데이터를 쓴다.
2. 팔로워 복제본이 해당 데이터를 동기화한다.
3. 리더 브로커가 장애를 일으키면 Controller가 새로운 리더를 선출한다.
4. Consumer와 Producer는 갱신된 메타데이터를 기준으로 다시 통신한다.

이 과정을 통해 장애가 발생해도 서비스 연속성을 유지할 수 있다.

## Bootstrap Server의 의미

Kafka 클라이언트 설정에서 자주 보이는 `bootstrap.servers`는 "클러스터 전체 주소 목록"이라기보다 "초기 접속 지점"이다.

```properties
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
```

클라이언트는 이 서버들 중 하나에 먼저 접속해 클러스터 메타데이터를 받아온다. 이후에는 메타데이터에 포함된 실제 리더 브로커와 직접 통신한다.

즉, bootstrap server는 데이터 자체를 대표하는 서버가 아니라 클러스터 정보를 얻기 위한 진입점이다.

## 실무에서 자주 생기는 오해

### 1. bootstrap server 하나만 있으면 그 서버가 모든 데이터를 처리한다
아니다. 초기 연결만 담당할 뿐이며, 실제 데이터 송수신은 메타데이터에 따라 각 브로커로 분산된다.

### 2. controller가 데이터를 저장한다
controller는 메타데이터와 클러스터 상태 관리가 핵심 역할이다. 실제 메시지 저장과 송수신은 broker가 담당한다.

### 3. 토픽마다 하나의 프라이머리 서버가 고정된다
정확히는 토픽이 아니라 파티션 단위로 리더가 정해진다. 따라서 한 토픽 안에서도 여러 파티션 리더가 서로 다른 브로커에 분산될 수 있다.

## 정리

Kafka 클러스터를 이해할 때는 다음 네 가지를 명확히 구분하면 된다.

- Broker: 데이터를 읽고 쓰는 서버
- Controller: 클러스터 상태와 리더 선출을 관리하는 서버
- Partition Leader: 특정 파티션의 읽기/쓰기 기준점
- Bootstrap Server: 초기 메타데이터 조회용 접속 주소

이 구조를 정확히 이해하면 리더 변경, 복제 지연, 브로커 장애, 클라이언트 재연결 같은 운영 이슈를 훨씬 수월하게 해석할 수 있다.
